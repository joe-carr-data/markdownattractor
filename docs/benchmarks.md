# Benchmarks

Numbers measured on this repository, never tuned to look good. Corpora are fixed before results are seen (plan §11). Apple M3, 24 GB, macOS 15, release builds unless stated.

**How to read this page.** The benchmark programme (strategy `docs/plans/2026-09-benchmarks.md`, rules 0.1–0.9; execution `docs/plans/2026-09-benchmark-execution.md`) measures five axes, each with one or two published tables: **A** retrieval (does the index find the page?), **B** answer quality and token economy (does Claude answer as well while reading less?), **C** freshness (how long until a change is found?), **D** time (does the index know when things changed?), **E** cost and size (what does a build cost, how big is the artifact?). Every published table was preceded in git by its `FROZEN.md` and a passing preflight, every number on it is rendered by a script from committed artifacts (never retyped), every comparator pair carries a paired bootstrap interval, and a claim is made only where its preregistered gate passed. Every model call went through the owner's Claude Code login (Astra's panel verdicts through the owner's Codex login); list-price figures are what the same calls would cost on the API. The development and exploratory rows that led to the tables (2026-09-22 to 2026-09-25) are in `docs/archive/benchmarks-development-2026-09.md`, verbatim. The reproduction runbook is `evals/benchmark_it_with_claude.md` (§7 per table).

**Headline claims, as measured** (generated by `scripts/eval/t6.sh readme-row` from the committed analyses and rows; limited to the gates that passed; the same table is in the README):

## Axis A — retrieval

The published table is T1 (the DocsQA-Repo test split, scored once). The golden set is this repository's fixed retrieval set, measured first; the DocsQA development rows, the competitor arms on the dev split, the tuning loop and the pooled-label diagnostic are in the archive.

### Retrieval — golden set (`evals/golden`, 32 docs, 117 sections, 60 queries, 16 temporal)

A query's expected sections are alternatives (any of them answers it), so the headline metric is **success@5** (an expected section is in the top 5); **MRR@5** is the mean reciprocal rank of the first expected section within the top 5. The plan calls this recall@5; the eval harness names it precisely.

`mda eval --golden evals/golden -k 5`, cards recorded once with Haiku 4.5 through the `api` backend ($0.31, 117 cards, 0 failures, 45 s).

| Run | success@5 | MRR@5 | mean query, in-process |
|---|---|---|---|
| lexical, raw text only (no cards) | 0.883 | 0.747 | 0.8 ms |
| lexical, cards + raw | 0.900 | 0.777 | 2.2 ms |
| **hybrid, cards + raw + vectors** (bge-small-en-v1.5-q) | **0.983** | **0.853** | 60 ms |

- G5 asks for success@5 (the plan's recall@5) ≥ 0.85: met by every run; hybrid leaves one miss out of 60 ("ship a new version of the API" → the v1 deprecation section outranks the release runbook).
- The seven lexical misses were all paraphrases ("undo the last release", "mass logout incident", "escalation policy for outages", "new hire reading list", …); vectors recover six.
- Hybrid query time is the query embedding (ONNX on CPU), not the scan: the dot-product scan over 117 vectors is microseconds, and the same scan over 10K synthetic 384-d vectors is under 10 ms.

### Search latency — CLI process on `docs/` (18 files, 163 sections)

| Command | p50 wall (fresh process) |
|---|---|
| `mda search … --raw` (lexical) | 20 ms |
| `mda search …` (hybrid) | 257 ms, of which ≈ 200 ms is loading the embedding model |

The MCP server keeps the model loaded, so a tool call pays the ≈ 50 ms embedding, not the load. The plan's 30 ms hybrid budget is not met by the query embedding itself; lexical search meets it with margin. Levers if it matters: a smaller query encoder, ONNX thread settings, or caching query vectors.

#### What travels with the table

T1 reuses the M2 artifacts (the committed cards, the qmd indexes, the BM25-over-files tables, the archived graphify graphs); it is not a fresh-build comparison, and every artifact's hash is in `T1/FROZEN.md`. graphify's Sonnet-built graphs exist for Tailwind and Supabase only (its builds did not complete on Prisma and GitHub Docs, recorded); its Haiku-built graphs exist for all four. The freeze was re-written during the run for driver and script fixes with identical inputs; each arm's manifest names the commit its rows were produced under, and the chronology is the git history of `T1/FROZEN.md`. The qmd and graphify drivers collapse whitespace in the question; mda receives it as written. graphify nodes without a source file are dropped (they name no page). The CPU and GPU chains ran concurrently, so the drivers' own timings reflect contention; the published latency was measured afterwards, alone, with the judging chain (network-bound) running beside it; "cold" means a new server process, not cleared model or query caches. The preflights (`evals/results/docsqa/preflight/T1-<project>.json`) passed every check on Tailwind, Prisma and GitHub Docs; on Supabase every check passed except one activation probe for the graphify-haiku arm, in two attempts (question `supabase-13977`: the headless agent read files instead of calling the graph tool; the arm's rows come from the tool directly and are unaffected; both attempts are committed). Codex's M4 pass on the scorer, the drivers and the freeze (`docs/reviews/codex/2026-09-24-bench-m4.md`) preceded every number on this page.

## Axis B — answer quality and token economy

Two published tables: T2 (the DocsQA-Repo test split) and T6 (the T2 method on our own corpora: the golden set, this repository's `docs/`, and a private corpus as supporting evidence). No savings claim passed its gates on either: on DocsQA the non-inferiority gate fails for most pairs and the grounding gate for every arm; on our public corpora the two quality gates pass for every pair and the grounding gate alone fails (on the private corpus one pair also fails the non-inferiority gate). ## Where we lose

Each table's own reading carries the numbers; this section says where they point, without restating them.

- **Axis A.** Against qmd full, the hybrid row's misses that qmd recovers are mostly pages the hybrid ranked sixth to tenth: qmd's reranker reads the candidate text and reorders, which mda does not do (T1, "Where we lose"). Against the model-free BM25-over-files control on Tailwind, a whole-page index scores above the hybrid row on long hub guides that a community question matches as a whole page rather than as one section. Every T1 point estimate is at or above qmd full's, and every paired interval includes zero: not behind, not distinguishably ahead on these sample sizes.
- **Axis B.** No comparator pair passed the three gates on any DocsQA project: the grounding gate (every factual claim about the product supported by a cited page, ≥ 95%) fails for every arm, mda included, so the consumption differences are measurements, not savings. mda's mean score is below qmd's on Prisma on the original grades. On the golden corpus the index read more source tokens than grep-and-read, and the page said so from the first run (archive).
- **Axis C.** For an exact-token lookup the grep arm's answer endpoint is faster than any index arm's: the question hands the agent a unique literal. mda's save → card p50 meets the G1 threshold on one machine; its answer endpoint does not beat a direct text search on that workload.
- **Axis D.** No pair earns the preregistered "correct with less effort at equal evidence" claim: with `.git` and `git` in Bash, every arm, mda included, opens git first; mda consults its index on top and so makes one more median tool call and reads more source tokens. Only mda vs qmd on Prisma has a correctness interval excluding zero.
- **Axis E.** mda's first build costs money (Haiku cards per section) where qmd's is free local compute; a build-cost comparison across arms is fair only at matched models and outputs, and the table says so.
- **Corpus size.** The small-corpus end is where grep-and-read is cheapest, and T6 shows it: on the golden set (32 files) mda's median run read 1,240 source tokens against grep's 672 and cost a tenth of a cent more; on `docs/` (73 files) it read 1,948 against 3,259 and cost less. Quality is at parity or above on both (every gate-(a) lower bound ≥ −0.25, mda vs grep on `docs/` +0.28 with an interval excluding zero), and nothing is claimed because the grounding gate fails: on the golden set mda's own embellished claims (0.90 against the comparators' 0.98); on `docs/` unresolved bare-token citations (a mentioned file extension, a file named outside the corpus) explain most failures for every arm alike, unsupported claims and answers without a resolvable citation the rest — counting every unresolved-only row as grounded would still leave three of four arms below 95%.

## What the model already knew (rule 0.6)

The answering and grading models are Claude models; what they already know contributes to every arm alike and is described per corpus, never asserted absent.

- **DocsQA-Repo (T1, T2, T4, T5).** Public documentation of widely used projects (GitHub, Prisma, Supabase, Tailwind CSS) at pinned commits. An agent can answer many community questions from prior knowledge without retrieval; T2's grounding check is what catches an answer that is right but unsupported by a cited page, and its failure rate (every arm, every project) is the measure of how much of the answering did not come from the pages. T5's questions ask for dates of changes inside a specific window of a repository's history; those are not in any training set at that resolution, and the traces show every arm reaching for `git`.
- **The golden set (A; T6).** Fictional platform-team notes written for this repository. The vocabulary (runbooks, ADRs, postmortems) is ordinary and the facts are invented; prior exposure and performance without retrieval were not measured, so the invented facts are a reason to expect retrieval mattered, not a demonstration.
- **This repository's `docs/` (T6).** The model knows Rust, Claude Code and markdown tooling in general; this project's decisions, dates and numbers are specific to it; prior exposure and performance without retrieval were not measured. The answering model also knows this plugin's *shape* from the pages it opened in the same run and from the skill it was given (the search-first rules name the MCP tools), which is how an answer can call a tool `mda_open` where the cited design page says `mda open`: the grader counts that as an unsupported claim, and T6's grounding table shows where it happened.
- **The private corpus (T6, supporting evidence only).** The owner's own research notes, unpublished by the owner's account; prior exposure and performance without retrieval were not measured. Nothing content-bearing is published; its separately headed tables carry counts and rates only.
