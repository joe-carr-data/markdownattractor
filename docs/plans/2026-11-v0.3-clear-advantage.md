## Where we stand (from the published benchmarks, no new measurement)

- **Ahead:** search latency against qmd (T1: under a second against 42–47 s on three corpora); save to raw-searchable p50 1.7 s, to card p50 8.4 s (T4).
- **Level:** answer quality against grep, qmd and graphify; one edge, +0.28 against grep on this repository's `docs/` (T6, interval [+0.04, +0.56]).
- **Behind:** grounding on the golden set, **89.6 % for mda against 97.9 % for grep, qmd and graphify** (T6: 5 ungrounded rows of 48 against 1; "mda's answers, written from a card and the opened section, embellish more often"; one of the five was a last-updated date the page does not carry). - **Not established:** fewer source tokens at parity (G3).
- A product whose claim is trust scores lowest on trust on its own demo corpus. That is fixed before anything is added.

## The bet

A pre-built index beats search-and-read only where one read cannot know the answer. The bet is **change-impact review**: when a section changes, find the other sections that still state the old thing, and show both passages with their lines and dates. Positioning if it passes its gate: "Change a decision. Find the docs that still describe the old behaviour."

Why this one: it has a trigger (a change), a bounded search (the changed section's neighbours) and an action (review two passages), and it uses what the index already holds: the watcher, section hashes, history, evidence-checked extraction. The spike (2026-11-15, lexical candidates and a Sonnet judge): 0 real contradictions in 297 judged pairs on uv, FastAPI and Backstage docs, 1 real in 57 on this repository's docs (the charter's "no API key", fixed in PR #71). So: value on working docs, none as a stunt on polished ones, and whole-folder scanning is the wrong shape; a change is the right trigger.

Known weakness: a prompt that compares two passages is easy to copy. The advantage has to be low noise, measured.

## Phase C design v2 (2026-11-17, after the Codex design pass)

Phase C starts 2026-11-17; the stop rule is checked at the end of 2026-11-19. v1 was reviewed before any code (`docs/reviews/codex/2026-11-17-change-impact-design.md`: rework, 14 findings, all accepted); this is the design that is built.

### What the feature says, and what it never says

After a change to one markdown section, mda names other sections that are **possibly** out of date under a scope the two passages demonstrably share, and shows the evidence: what the changed section said before, what it says now, and what the other section says, each as an exact slice of its source with file and lines, plus the index's last-changed dates with their source. It never says which passage is right, never recommends an edit, and never edits anything. A review that could not cover everything says what it did not cover; missing coverage is never shown as "no findings".

### C1 scope (about a week), and what is cut from it

C1 is `mda check [--since <revision>] [--max-judgments N] [--all] [--json]`: lexical candidates plus links, one judgment per pair, CLI and JSON. Cut from C1 and deferred to C2 (only if the gate passes): entity and embedding candidates, the MCP tool, review by the daemon, any stored findings or judgment cache (so **no schema change in C1**), recovery of renamed files and moved or renamed sections, and review of additions beyond the simple rule below. Not cut: scope-aware evidence, a fresh snapshot, safe git and FTS handling, bounded spend, backend failure handling, the candidate-recall measurement, the frozen evaluation.

### The snapshot

1. Resolve `--since` once to a commit id (default `HEAD`). It must be an ancestor of `HEAD`; otherwise the command refuses with one line. Git unusable, an invalid revision, a missing blob or a shallow history that does not hold the revision are each reported as such, and are different from a completed review with zero findings.
2. Bring the raw index up to date with the working files (parse only, no model call), so a file saved a second ago and a file never indexed are both in the review.
3. Before printing, re-read every file that takes part in a finding. If its content hash moved during the review, the finding is withheld and counted as `stale_during_review`; line ranges are refreshed from this last read.

### The unit: a change

Before = the file at the revision (`git show`, with the repository prefix applied when the watched root is below the repository top level; bounded, shell-free git calls as in `gittime`), parsed with the file's own flavour. After = the working file. Line endings are normalised for the comparison only; this is not ADR-0008's dating eligibility, which would reject the uncommitted edits this command exists to review.

Pairing sections of one file: first pair sections whose hash is unchanged (not changes); then pair what is left by heading path when that heading path is unique on both sides. Everything else is **not paired**: a renamed file, a renamed or moved heading, repeated headings whose order changed. Unpaired sections are counted and listed as `not_reviewed` with the reason, never treated as additions. A section that exists only after, in a file that also exists before, is an addition and is reviewed with its own wording as the query. Deletions are not reviewed.

### Step 1 — candidates (no model)

- **Terms** from the changed lines, the removed side first (a stale copy still carries the old wording): at most 12 terms, identifiers first (code spans, numbers with their unit, paths, versions, CamelCase and snake_case words), then the rarest words by document frequency; stop words and terms present in more than 20 % of sections are dropped. Terms are passed to FTS as quoted literals with no prefix operator; query length is bounded. File content never becomes query syntax.
- **Sources:** (a) lexical over raw section text; (b) sections of documents that link to the changed document or that it links to, kept only when they share at least one term.
- **Fusion and caps:** deterministic. Linked sections first, then lexical by rank, at most 2 sections per document, 8 candidates per change. Judgments are dealt round-robin across changes (each change gets its first candidate before any gets its second) up to `--max-judgments` (default 40).
- **As built (2026-11-18, `impact::candidates`), where it differs from the three lines above:** a term is dropped as common only above the larger of 20 % of sections and 10 sections (a small folder would otherwise lose every term), and a term no section carries is dropped too; sections carrying a term of the change's leading role (the replaced wording when there is any) come before sections that only share other terms, and "linked first" holds inside each of those two groups, so a linked index page sharing one topic word cannot push out a stale copy; a section whose text equals the changed section's new text is not a candidate; linked documents are searched up to 50 per change, and the number left out is counted; ranked hits are read page by page until the eight places are filled, so the counts are `matching` (sections sharing a term), `examined`, `cut_per_document`, and two flags for what was not looked at (`scan_truncated` after 400 hits of one search, `terms_unexamined` after 400 term lookups) in place of "retrieved" and "cut by caps" (Codex review 2026-11-18, nine findings). Links are read from the index's stored targets and resolved as text (no schema change).
- **Counts in every output:** changes found, not reviewed (by reason), candidates retrieved, cut by caps, judged. Candidate recall (is the labelled document among the candidates?) is measured in the evaluation before any judging.

### Step 2 — judgment

One call per (change, candidate) pair. Input, each part delimited as untrusted data: the before text, the after text, the changed lines; the candidate section; and for both documents the path, the heading path, the front matter and the document's title and opening lines (bounded), so that a version, a status ("archived", "deprecated"), a changelog or a template is visible to the judge. Dates are not sent: a newer date must not decide a verdict.

Output, by JSON schema:

- `verdict`: `possibly_outdated` (the candidate still states, as a current instruction or fact in the same scope, what the change replaced), `possible_conflict` (both state current facts in the same scope that cannot both hold), `related`, `unrelated`, `abstain`.
- The judge is told to abstain when the shared scope cannot be shown: another version or product, a changelog, release notes, an archive or decision record that is meant to keep the old statement, an example or template, a translation or generated copy whose source is elsewhere.
- `before_quote`, `after_quote`, `candidate_quote`. `possibly_outdated` needs all three; `possible_conflict` needs `after_quote` and `candidate_quote`. Each is located in its own snapshot by the cards' normalised matching, must be non-empty and match exactly one place, and is then **rendered as the exact source slice at the located offsets**, not as the model's string. A miss or an ambiguous match drops the finding (`dropped_unquoted`).
- `reason`: one sentence, shown labelled as the model's reading.

**As built (2026-11-18, `impact::judgment`), where it adds to the lines above:** "dates are not sent" means the index's dates; a date an author wrote in the text or front matter is part of the passage. An alert is also dropped (`dropped_unquoted`, with the failing quote named) when its change-side quotes are not on lines the change touched or carry none of the wording it replaced or brought in, when the candidate's quote carries the new wording and none of the old, or only words of the after quote, and, for `possibly_outdated`, when it carries none of the replaced wording: the evidence must be about the change. This is a word-level rule and loses a stale copy that is a paraphrase; the evaluation counts it. A match must begin and end on whole source characters. The model's reason is left out of a finding when it takes a side or asks for an edit. The judge is told the other section is shown "as it reads now", not that the change left it untouched (Codex review 2026-11-18, six findings).

`supersedes` (a passage that itself says it replaces the other) is deferred; C1 makes no authority claim at all. Alerts are deduplicated per (change, candidate document).

- **Backend:** one new object-safe method on `Backend` taking a request envelope (system prompt, user text, JSON schema, output cap) and returning a result that carries usage on every variant, including refusals and failures, with usage explicitly unknown when the backend did not report it. Implemented for `api`, `local`, `claude-cli` (tools disabled, as for cards), `mock` and `unavailable`. `summarize` is not refactored in the same change.
- **No backend:** candidates are printed as "not judged (no summarization backend)"; exit 0; never called alerts.
- **Spend:** `--max-judgments` caps pairs; each pair gets at most one retry; the input per pair is capped (a pair above the cap is `not_reviewed: too_large`), as are output tokens and time per call. On `claude-cli`, which has no output-token flag, the output cap is applied after the call (an answer above it is rejected) and the per-call dollar budget bounds the spend. Calls run one at a time. Every attempt, whatever its outcome, is written to `usage_log`. The remaining daily budget is read before each call and the run stops when it is used up; with a daemon spending at the same moment this is a check before each call, not a strict ceiling, and the documentation says so.

### Evaluation

- **Mining (`scripts/eval/c_mine.py`, no model) produces hypotheses, not labels:** a commit A that modifies markdown file X, and a later commit B within 60 days that makes the same replacement in another file Y that A did not touch and that carried the old wording at A.
- **Confirmation:** the panel (Opus 5.5 first, Fable, Astra) sees only what existed at A — X before and after, and Y at A — never B, and answers: same referent, same applicable version, an actual inconsistency at A? Two of three confirm; a pair that is rejected or split is dropped and counted. Only confirmed pairs are cases.
- **Ordinary commits** (the same number, same repositories, no mined follow-up) are unlabelled. They support no true-negative claim; every alert on them is adjudicated.
- **Run:** per case a clone that holds history only up to A (the object graph is checked: no later commit, tag, alternate or remote; no network), an index built only from A, no stored cards or judgments from elsewhere, then `mda check --since A^` with the `claude-cli` backend through the owner's login. Baseline: Claude headless with grep, file reads and git on the same clone, the same model, asked to list documents the change left possibly out of date. What cannot be isolated is the models' prior familiarity with public repositories; the result says so.
- **Metrics, frozen before the first scored run:** *precision* = confirmed alerts over all emitted alerts, deduplicated per (case, affected document), every alert adjudicated blind to the arm. *Mined-label recall* = confirmed (case, affected document) labels alerted, over all such labels; cases cut by caps, partial runs and abstentions count as misses. Cost = the marginal cost of the check at list price, for both arms, uncached; indexing cost reported apart. Comparisons are aggregate over the test half.
- **Split by repository**, not by pair: development repositories for at most two prompt iterations, test repositories scored once. The test half needs at least 8 confirmed cases and at least 8 alerts; below that the gate is reported as **unmeasured**, never as passed.
- **What a pass may claim:** a feasibility result on replacements that were later repeated elsewhere, a kind that favours lexical retrieval and leaves out paraphrases, deletions and errors nobody fixed. With 15–30 cases, intervals are wide and are printed.
- **Development half, iteration 0 (2026-11-18, binary `dc5da35`, first 8 of 20 cases read while the run went on):** 1 of 9 labels alerted. The judge was not the limit: the mined commits change 9 to 304 sections each, so 40 judgments dealt one per change in file order rarely reached the labelled pair (4 labels above the cap), a replaced identifier still carried by 106 files cannot be covered by 8 candidates, one label sits in a section the change renamed (not paired, by design), one in a hidden folder the index does not read, and valid answers were rejected by a 700-token output cap that `claude-cli` exceeds. **Iteration 1 (system, not prompt; counted as the first of the two):** pairs ordered by how rare their shared replaced wording is, repeated pairs judged once, output cap 1,500. A label is scored per (case, document) as the metric says; whether the finding hangs on X itself is reported apart.
- **Iteration 0 in full (20 development cases, binary `dc5da35`):** 8 of 23 labels alerted (5 from X itself), 64 alerts, 716 judgments, $7.48 at list price. Missed: 7 never judged (the cap), 6 never candidates, 1 dropped quote, 1 abstain. **Baseline on the same cases** (Claude Haiku headless with search and read-only git): 11 of 23 labels, 58 documents listed, $4.12; one case without an answer. Precision of both arms is being adjudicated. **Iteration 2 (the second and last):** the order of iteration 1 reworked after its Codex review (one pair per change in turn, strongest first, repeats last); a replacement that only changes capitals is a replacement (`db.sql.public.user` to `…User` was read as context); a quote that stands several times is settled on the changed line, or at its first place when it is a phrase, not refused; a candidate quote is "the same words" only when it is a part of the after quote word for word (a stale copy of "Helm 4 release" against "Helm 4 pre-release" was dropped).

Baseline (Claude Haiku with file search and read-only git): 11 of 23, 52 alerts, 45 confirmed (87 %), $4.12. Precision is below 80 % after two iterations, so the rule fires; and recall is below the baseline's at a higher cost, so the gate could not have passed either. The test half (16 cases) was never run.
