# Plan — M8: T5, the simulated historical replay (drafted 2026-09-27, starts on "go M8")

Milestone M8 of the execution plan (`2026-09-benchmark-execution.md` §4 T5, §5 M8): axis D, the time model. A fixed commit range per repository is replayed step by step into mda's store under a test-only clock override (`MDA_NOW`), the stored timestamps are validated against `git log` (a failed validation voids the replay), and forty questions per project with git-computed ground truth are answered by every arm, each arm given the same `.git` and allowed to read history in Bash. The comparison is correctness and effort at equal evidence, never "the others score zero" (plan §1.2, §1.3). Acceptance: the table is complete whatever it shows; the claim "correct with less effort at equal evidence" is made for a pair only under the preregistered criterion of §4 T5.

## Decisions carried in

- **Projects: Prisma and Tailwind CSS** (the two smaller corpora; the pinned commits `c4ac0e9` and `bd868a3`). Supabase and GitHub Docs are excluded from the replay for cost and step count (their histories touch hundreds of pages a week) and the page says so; T5 is labelled a simulated replay on two corpora. If the dry-run cost estimate (H2) for the two comes in under $15 list-price, Supabase is added before the freeze; the freeze names the final set.
- **Replay clones, never the pinned checkouts.** The pinned checkouts are shallow (one commit); deepening them modifies them. Each project gets a fresh clone under `$RUN/t5/<project>/src` fetched to full depth for the range (`git fetch --deepen` until the range start is reachable), checked out step by step. The T1–T4 artifacts stay untouched (hashes checked by the freeze).
- **Range and steps.** The range is the 60 days ending at the pinned commit's author date; a step is every calendar day (UTC) with at least one commit touching the corpus paths, taken at the last such commit of that day; the pinned commit is the final step. The step list (sha, author date) is generated once, committed as `T5/<project>/steps.jsonl`, and hashed in the freeze. Daily steps keep `first_seen_at` within one day of the adding commit, which is the resolution the "when" questions are scored at.
- **The clock.** `MDA_NOW=<RFC 3339>` is read once by a single `mda_core::clock::now()` that replaces every non-test `Timestamp::now()` in `mda-core` (17 call sites today: pipeline, store, search, daemon, timefmt). Malformed values refuse to start (fail closed, `Error::Config`). Unset means the real clock; nothing else changes. Recorded in an ADR (test-only override, never documented as a user feature; the daemon refuses to start with it set, so a replay is always inline `mda index`).
- **Filesystem times at each step.** Every file changed at a step gets its mtime set to that step commit's author date (`git log -1 --format=%aI <sha> -- <path>`); at the first step every corpus file gets the author date of its last change up to that commit. Birth times cannot be set, so `created_at_source` is `first_seen` throughout (the clone's birth time postdates every mtime and is filtered out by `file_times`); `created_at` of a file present at the range start is the first step's date and the page says that history before the range is flattened to the first step. Questions are generated only about changes inside the range.
- **What is validated, exactly.** After the last step, per document: `updated_at` equals the author date of the last commit touching the file in the range; `first_seen_at`/`created_at` equal the first step at which the file exists (for files added in the range: the author date of the adding step, within one day of the adding commit); every section `updated_at` is one of the step dates and no later than its document's; tombstoned documents match files deleted in the range with `deleted_at` at the deleting step. Written to `T5/<project>/validation.json` with the mismatch count; any mismatch voids the replay for that project and the page says so (plan §4 T5).
- **Questions: 40 per project, three types, generated from git, seeded.** (a) *which*: "Which pages under `<dir>` changed between D1 and D2?" and "Which sections of `<page>` changed between D1 and D2?" — ground truth the set from `git log --name-only` / the section differ on the two blobs; scored set F1 ≥ 0.8 → 1 else 0; (b) *when*: "When was `<page>` last changed?" and "When was the section `<heading>` of `<page>` added?" — within one day of the git date → 1 else 0; (c) *added in month*: "Which pages under `<dir>` were added in <month>?" — set F1 as (a). Candidates are enumerated exhaustively from the step list, kept only when the ground-truth set has 1–12 members (answerable, non-trivial) and the dates are inside the range, then 14 / 13 / 13 are drawn in `eval::seeded_order(seed 20260922)`. Naming the page is allowed here (the tool under test is the time index, not retrieval; T4's lesson concerned tool activation proof, which the T5 preflight probes cover separately). Stored as `T5/<project>/questions.jsonl` with the question text (generated, no third-party text), the ground truth and its git evidence (shas, paths, dates).
- **Arms.** *git baseline*: Claude with Bash (`git log`, `git diff`, `git blame`) and Read, no index — the reference for "equal evidence". *mda*: MCP (`mda_search` with `since`/`until`, cards with dates, `mda_open`) plus Bash on the same clone. *qmd*: its MCP on an index built at the final step (qmd has no time model; disclosed) plus Bash. *graphify*: its archived graph for the project (Tailwind: the Sonnet build; Prisma: the Haiku build, labelled) plus Bash. grep is subsumed by the git baseline (Read/Grep/Glob plus Bash git) and is not a separate arm. Every arm is launched through `lib.sh arm_launch` on the replay clone (`ARM_CORPUS_OVERRIDE`) with Bash added to the allowed tools for T5 only; the launch configuration is what the preflight probes.
- **Answers are structured.** Every run answers through `claude -p --json-schema` with `{pages: [..], sections: [..], date: "YYYY-MM-DD", evidence: [..]}` (the fields the type needs); scoring is deterministic and needs no grader. Effort per run: tool calls (`tool_use` blocks), source tokens (T2's signed, clipped accounting from `message_delta`), turns, wall-clock, list-price cost; recorded as in T2 rows.
- **Runs and analysis.** 3 runs per question and arm (rule 0.4's shape), question-level medians of correctness and of each effort measure with failed runs as 0 correct and their effort as recorded; a 10,000-draw paired bootstrap over the 40 questions (seed 20260922) for mda vs git baseline and mda vs each other arm; the claim "correct with less effort at equal evidence" only when the correctness difference's lower bound ≥ −0.05 **and both** effort differences' upper bounds (tool calls, source tokens) are < 0. Implemented in `mda_core::eval::analysis` as a replay analysis (new input shape, same bootstrap and manifest validation), exposed as `mda eval --replay-analysis`; the page publishes every pair with or without the claim.
- **Cost, estimated before the go.** Replay: the first step is a full build of the range-start snapshot (T3: Prisma ≈ $4–5 at Haiku, Tailwind ≈ $1), then hash-keyed increments (changed sections only); runs: 40 × 3 × 4 arms × 2 projects = 960 answers ≈ $0.05 each ≈ $48 list-price, ≈ 7.5 h at the M5 pilot's 132 runs/h. Every call through the owner's login; list price is reporting only.

## Exit criteria

- [ ] `validation.json` per replayed project committed with zero mismatches, or the project's replay voided and the page says so.
- [ ] 40 questions × every arm × 3 runs has a row per project (a failed run is a row).
- [ ] The T5 freeze precedes every row in git; the pinned checkouts and the T1–T4 artifacts are unchanged (hashes checked); the table regenerates byte-identically from the archived rows (`RUN=$T5_REGEN`).
- [ ] Every comparator pair is published with its three intervals; the claim appears only where the preregistered criterion holds.
- [ ] Runbook §7.5 reproduces setup, replay, validation and runs on a fresh machine; `MDA_NOW` is documented as test-only in the ADR.
