## Verdict (Codex, condensed)

"The bounded-build design is a defensible benefit; 'cheaper indexing than the alternatives' is not established." For the two completed graphify builds mda has the lower reported list-price equivalent ($6.51 vs $10.25; $30.48 vs $47.17) but graphify finished faster (13.8 vs 19 min; 34.2 vs 89 min). What makes the broad claim unsound: unequal models (Haiku vs Sonnet; rule 0.6 allows whole-system comparison but it then describes configurations, not architecture); different artifacts (a graph with relations and images, not rewarded by DocsQA); subscription accounting (list-price equivalents are neither charges nor a measured fraction of an allowance; cache reads, cache writes, uncached input and output need separate reporting); the parent's polling turns belong to our headless host-agent execution, not necessarily to graphify; graphify caches semantic extraction too (the defensible distinction is section-level vs file-level invalidation plus measured orchestration overhead); qmd builds with zero remote tokens. Accepted wording today: *"In these development runs, mda's Haiku card generation had lower reported list-price equivalents than the completed Sonnet graphify builds on Tailwind and Supabase, but took longer. The configurations used different models and produced different artifacts; graphify's measured usage included headless agent orchestration. Qmd built locally without remote model usage."*

What T3 must show: one row per project × named configuration × operation (first build; one-edit update), with configuration (tool, resolved parent and extraction models, prompt/skill hashes, Claude Code version, workers, waiting policy), input (same pinned tree; files, common section count, bytes, images processed), completion state and coverage denominator, time split (active vs quota waiting; parse/extract/embed/merge), remote usage by category (parent vs extraction agents; calls, retries, polling turns), dollars (CLI list-price equivalent, labelled), normalisation per 1,000 common input sections (never per card, node or chunk), storage (index, incremental cache, shared model downloads), provenance (attempt logs, hashes, cache state, machine load, freeze status). First-build timing produces cards and embeddings from scratch (attaching committed cards is reconstruction). qmd's totals are 162 / 397 / 496 / 1,397 s (add + update + embed), not the embedding-only 161 / 394 / 494 / 1,390. Failed attempts are kept separately with cumulative spend; single measurements say "one run". A future measurement-shaped headline: *"After one frozen section edit, mda refreshed its searchable cards and vectors in X s using Y remote tokens ($Z equivalent), versus A/B/C for graphify-Haiku and D s with zero remote tokens for qmd"* — filled only after measuring the same endpoint; "incremental cost near zero" is a hypothesis until then.

Haiku: yes as a separate, uniformly built **graphify-Haiku** configuration on all four projects (record parent and every subagent model; never resume a Sonnet extraction cache in a "clean" Haiku build; a mixed graph is labelled mixed with cumulative cost); keep graphify-Sonnet where it completed and never suppress it if its quality is better; a per-project model switch after failures is an adaptive change, not one arm.

Incremental cost: start from a completed, validated index with its normal caches; the same predeclared sentence edit to one section; mda: detection, changed-section card, embedding, persistence, availability through retrieval; graphify: the documented `/graphify <path> --update` skill flow through the login (docs need the model; the CLI's `graphify update` re-extracts code only); qmd: `qmd update && qmd embed`; the timer stops when the refreshed artifact is available and correct through the normal query interface; T4 keeps save → correct grounded answer as its own endpoint. **The execution plan's T4 line (`graphify update`) needs the docs-aware clarification before execution.**

Weekly limit: publishable as an operational event (timestamp, exact message, attempts affected), not as "consumed the whole weekly plan" (initial remaining allowance, other sessions and model-specific limits unknown). Accepted wording quoted in the runbook.

Blockers found in the files: runbook §4c said "by far the most expensive step" (not established) and that Prisma and GitHub Docs "were rebuilt with Haiku" while their records said did not complete; the Supabase record's token totals (64.6M input / 171K output, from the final result event's `usage`) disagree with the transcript's `modelUsage` (75.0M cache-read / 5.5M cache-creation / 1.78M output) — reconcile parent/child inclusion before publishing ratios; failed records lacked models, tokens, dollars and attempt provenance; coverage populations differ (dataset pages vs source files: 4,860 vs 5,469) and must be labelled; graph paths were local cache paths, the graphs must be durably published; "qmd has no model call" → "no remote model calls; local embedding inference".
